Назад до змісту лекцій

Лекція 1. Роль, типи та архітектура програмної документації

План лекції:

  1. Документація як інженерний інструмент: задачі, аудиторії, типові проблеми.
  2. Класифікація програмної документації: продукт vs процес, категорії, ЄСПД.
  3. Архітектурні документи системи: SSD, SDD, ISD та ADR.
  4. Документація як засіб забезпечення супроводжуваності: простежуваність (RTM), актуальність, handover.

Питання 1. Документація як інженерний інструмент

Документація давно перестала бути «додатковим артефактом», що створюється на завершальній стадії розробки. Це повноцінний інженерний інструмент — структурований носій знань.

  • Згідно зі SWEBOK, технічне письмо та управління документацією — окрема область знань, що підтримує всі процеси життєвого циклу ПЗ: від вимог до супроводу.
  • Забезпечує відтворюваність рішень, прозорість процесів і довгострокову супроводжуваність.
  • Система без документації — чорна скринька: поведінку можна виявити лише зворотним інжинірингом.
  • У командах з 3–5 розробників архітектуру тримає колективна пам'ять; у Enterprise-масштабі (десятки сервісів, розподілені команди) неявне знання — критичне вузьке місце.

П'ять фундаментальних задач документації (1/2)

1. Збереження знань (Knowledge Preservation). Кожне архітектурне рішення, компроміс, вибір технології — зафіксовані з обґрунтуванням. Інакше нові учасники повторюють шлях проб і помилок → дублювання помилок і технічний борг. Документація перетворює індивідуальний досвід на організаційний капітал.

2. Онбординг нових співробітників (Onboarding). Time-to-Productivity прямо залежить від якості документації: структурована архітектурна документація зменшує час онбордингу на 40–60%; без неї — тижні читання коду та питань колегам.

3. Комплаєнс та аудит (Compliance & Audit). Системи з даними користувачів підлягають вимогам GDPR, HIPAA, PCI DSS; ISO 9001, ISO/IEC 27001, CMMI рівня 3+ вимагають документованих процедур. Без документації аудит неможливий.

П'ять фундаментальних задач документації (2/2)

4. Комунікація між стейкхолдерами (Cross-stakeholder Communication). Аналітики, менеджери продуктів, розробники, тестувальники, DevOps говорять різними «мовами».

  • Документація — спільний референс, контракт, який усі приймають як джерело істини (Single Source of Truth).
  • Вимога, зафіксована в SSD, однозначно інтерпретується і бізнесом, і розробником, і QA.

5. Зниження ризиків (Risk Mitigation). При відході ключового розробника (Bus Factor = 1) документація — єдиний страховий механізм передачі знань.

  • Проєкти з критичними знаннями в одній-двох людях — найвразливіші до кадрових ризиків.
  • Документація децентралізує знання, підвищуючи стійкість проєкту.

Аудиторії документації та їхні потреби

Документ «для всіх» не задовольняє нікого: розробнику — занадто поверхневий, бізнесу — занадто технічний. Практика — сегментація за аудиторіями.

Рівні абстракції: приклад платіжного сервісу

Одна й та сама система — чотири різні перспективи:

  • Розробник (інтеграція з API): схеми запитів/відповідей, коди помилок, приклади викликів, гарантії консистентності даних.
  • QA-інженер: сценарії поведінки при відмові, таймаутах, некоректних вхідних даних.
  • DevOps-інженер: інструкція розгортання, конфігурація змінних середовища, налаштування алертів.
  • Бізнес-стейкхолдер: які транзакції підтримуються і який SLA гарантується.

Аудиторії не ізольовані: структурна сегментація — у SSD вступ для стейкхолдерів, технічні специфікації — для розробників і QA; або окремі документи для кожної аудиторії, пов'язані через traceability-матриці.

Антипатерн 1: Documentation Decay

«Документація застаріває» — антипатерн, що повторюється з покоління в покоління.

  • Код постійно змінюється (фічі, рефакторинг, багфікси), а документація, створена один раз, часто не оновлюється синхронно.
  • Довіра падає → команда читає код як джерело істини → документацію ніхто не перевіряє — самопідсилювальний цикл деградації (vicious cycle).
  • Коренева причина: розділення коду та документації у просторі та часі — Wiki ≠ Git-репозиторій: немає механізму, що змушує оновлювати документацію при зміні коду.
  • Рішення: Documentation as Code (Лекція 2) — документація в репозиторії, ті самі рев'ю та версіонування, що й код.

Антипатерн 2: Dead Documentation

«Документація існує, але не використовується» — зустрічається не рідше за перший.

  • Команда витрачає сотні людино-годин на багатотомну документацію, але на практиці ніхто її не читає.
  • Причини: формальна мова, неприродна для розробників; сховище, куди ніхто не заходить; дублювання коду; надмірна деталізація — знайти рішення швидше з коду.
  • Характерний для організацій, що проходять сертифікацію CMMI / ISO 9001: документація «для аудитора», а не для команди → формальна відповідність при фактичній відсутності інженерної цінності.
  • Здорова практика: документувати лише те, що має споживача; якщо документ ніхто не читає — переробити або видалити.

Типові проблеми та шляхи вирішення

Додаткові проблеми: відсутність власника документа, відсутність регламенту оновлення, надмірна формальність, фрагментація (Wiki + Jira + Slack + особисті нотатки без єдиного індексу).

Питання 2. Документація продукту vs документація процесу

Документація продукту описує саму систему: функціональність, архітектуру, інтерфейси, поведінку, обмеження. Живе стільки, скільки продукт; змінюється синхронно з його еволюцією: SSD, SDD, API Docs, User Guide, ISD.

Документація процесу описує, як система створюється та підтримується — артефакт життєвого циклу з кінцевим терміном дії: Project Plan, Release Notes, Post-Mortem, Test Plans, Change Requests, Audit Reports.

Ключова різниця — життєвий цикл: продукт «живий» (еволюційний), процес «історичний» — фіксує факт у моменті; звіт про інцидент не «оновлюється», новий породжує новий звіт.

Межа не завжди чітка: ADR фіксує момент рішення (ознака процесу), але зберігається в документації продукту — він пояснює, чому система влаштована саме так.

ЄСПД — концептуальна основа, а не обмеження

Єдина система програмної документації (ЄСПД) — комплекс державних стандартів, спадок радянської системи (ГОСТ 19.x), адаптований в Україні як ДСТУ. Визначає склад, структури, форми та вимоги до документів: технічне завдання, технічний/робочий проєкт, програма та методика випробувань, керівництво програміста/оператора, формуляр, описання застосування.

  • У Waterfall була адекватною: чіткі етапи, кожен завершувався випуском формального документа.
  • В Agile / DevOps / Continuous Delivery жорсткий каскад — перешкода: за тижневими релізами документи застарівають ще до затвердження.
  • Помилково трактувати ЄСПД як «застарілий стандарт, що не стосується сучасних проєктів». Правильне розуміння — каркас мислення про документацію, а не жорсткий регламент форм.

Три аспекти концептуальної цінності ЄСПД

  1. Повнота складу. Перелік документів ЄСПД — чек-лист: навіть якщо проєкт не використовує форму технічного завдання, питання «чи є у нас зафіксовані вимоги?» залишається релевантним. SSD сучасного проєкту може існувати як User Stories у Jira та Markdown-файл у репозиторії, але концептуально виконує ту саму функцію, що й ТЗ ЄСПД.
  2. Ідея життєвого циклу документа. Послідовність «вимоги → проєктування → експлуатація» валідна незалежно від методології: навіть у Scrum вимоги передують реалізації, а реалізація — експлуатації.
  3. Культура формалізації. Уявлення про структуру, розділи, відповідальних осіб і статус затвердження — фундаментальне. Сучасні формати (Markdown, ADR, OpenAPI) замінюють паперові форми, але зберігають сутнісну структуру: контекст, рішення, наслідки, статус.

Питання 3. Архітектурні документи системи

Ядро технічної документації продукту — ієрархія, що відображає три рівні проєктування:

  • SSD (System Specification Document) — зовнішня поведінка системи: «ЩО система робить?»
  • SDD (System Design Document) — внутрішня структура: «ЯК вона влаштована?»
  • ISD (Infrastructure Specification Document) — інфраструктурне оточення: «ДЕ і НА ЧОМУ працює?»

Разом — повний архітектурний портрет системи: будь-який кваліфікований інженер розуміє її від бізнес-вимог до фізичного розгортання — без доступу до авторів.

Кожен документ має чітку межу відповідальності і не дублює інший: зміна на одному рівні тягне перегляд пов'язаних документів — нова вимога в SSD → новий компонент у SDD → нова інфраструктура в ISD.

SSD — специфікація вимог до системи

SSD визначає, що система робить і які її межі. Це контракт між бізнесом (замовником, стейкхолдерами) і технічною командою.

  • Не описує внутрішню будову — лише зовнішню поведінку: функціональні та нефункціональні вимоги, інтерфейси із зовнішніми системами, обмеження та допущення.
  • Питання SSD: які бізнес-цілі обслуговує? які сценарії підтримує? які системи інтегрує? які вимоги (GDPR, PCI DSS) задовольняє? які SLA гарантує?
  • Задає межі системи (system boundaries) → захист від scope creep — неконтрольованого розширення функціональності.
  • Архітектурне значення: відправна точка для SDD; компонент без трасування до вимоги SSD — over-engineering.

Структура SSD

# System Specification Document (SSD)
## 1. Вступ
    призначення документа, бізнес-контекст і цілі, глосарій термінів
## 2. Опис системи
    межі системи (System Boundaries), контекстна діаграма,
    профілі користувачів та ролей
## 3. Функціональні вимоги
    Use Cases / User Stories, бізнес-процеси і сценарії,
    правила валідації та обмеження
## 4. Нефункціональні вимоги
    продуктивність (Latency, Throughput, RPS),
    надійність (Uptime, MTTR, RTO/RPO),
    безпека (Authentication, Authorization, Encryption),
    масштабованість та ємність
## 5. Інтерфейси із зовнішніми системами
    API-контракти (вхідні), інтеграції зі сторонніми сервісами (вихідні)
## 6. Обмеження та допущення
    технологічні обмеження, регуляторні вимоги (GDPR, PCI DSS),
    допущення та залежності
## 7. Критерії приймання
    вимоги до приймального тестування, метрики якості (ISO 25010)

SDD — документ проєктування архітектури

SDD описує внутрішню структуру системи: модулі, компоненти, сервіси, зв'язки, API, моделі даних та архітектурні рішення. SSD — «що?», SDD — «як?».

  • Найбільш технічно насичений документ; аудиторія — розробники та архітектори.
  • Документує рішення, що визначають структуру системи:
    • архітектурний стиль: моноліт / мікросервіси / serverless;
    • патерни інтеграції: синхронний REST, асинхронний message queue, event-driven;
    • моделі даних: реляційна, документна, графова;
    • стратегії кешування, балансування, обробки помилок, консистентності даних.
  • Особливе місце — ADR (Architecture Decision Records): раціональна основа рішень — чому PostgreSQL, а не MongoDB; чому Kafka, а не RabbitMQ.

ADR — Architecture Decision Record

ADR — короткий документ, що фіксує конкретне архітектурне рішення, його контекст, розглянуті альтернативи, обране рішення та наслідки.

  • Зберігає раціональну основу (rationale) рішень: чому PostgreSQL, а не MongoDB; чому Kafka, а не RabbitMQ; чому моноліт, а не мікросервіси.
  • Без ADR через рік ніхто не пам'ятає, чому було прийнято рішення — нові розробники можуть ненароком порушити архітектурні принципи.
  • Формат: Статус → Контекст → Альтернативи → Рішення → Наслідки.

Приклад: ADR-002 — вибір Apache Kafka

# ADR-002: Вибір Apache Kafka для event-driven комунікації

## Статус: Accepted (2024-09-15)   ## Автор: О. Іванов, Архітектор

## Контекст
E-commerce потребує асинхронної комунікації між Orders, Inventory,
Notifications та Analytics. ~10 000 events/сек у пікових навантаженнях.
Вимагаються гарантована доставка, partition ordering та replay.

## Розглянуті альтернативи
1. RabbitMQ      — простіший, але обмежений throughput, без native replay
2. AWS SQS + SNS — managed, але vendor lock-in, складність replay
3. Apache Kafka  — висока пропускна здатність, partition ordering,
                   replay, але складніший в експлуатації

## Рішення
Apache Kafka (self-hosted на Kubernetes):
+ throughput > 100K events/сек з запасом для росту
+ partition-based ordering для events по order_id
+ replay для відновлення read-моделі та аналітики

## Наслідки
+ операційна складність (Kafka cluster, ZooKeeper/KRaft)
+ topic-схеми та schema registry (Avro)
+ навчання команди Kafka-патернів (consumer groups, idempotency)
+ збільшення інфраструктурних витрат

ISD — документ системної інтеграції та інфраструктури

ISD описує інфраструктуру та середовище виконання: SSD — «що?», SDD — «як влаштовано?», ISD — «де і на чому працює?».

  • Документує розгортання: сервери, контейнери, мережеву топологію, сховища даних, middleware, моніторинг, бекапи та відновлення.
  • Джерело істини для DevOps/SRE: розгортання, масштабування, усунення інцидентів.
  • Без ISD розгортання тримається на «племінних знаннях» (tribal knowledge) — неприпустимо для production.
  • Зв'язок із SDD: кожен сервіс SDD має deployment-конфігурацію в ISD; SDD — логічна архітектура, ISD — фізична реалізація.

e-commerce: SSD — вимоги

Фіксує бізнес-вимоги та межі системи:

Функціональні вимоги:

  • Реєстрація та автентифікація користувачів.
  • Перегляд каталогу з пошуком та фільтрацією.
  • Оформлення замовлень з кошиком.
  • Оплата через платіжний шлюз (Stripe).
  • Відправка email/SMS-сповіщень.

Нефункціональні вимоги:

  • Обробка 5000 RPS у піковому навантаженні.
  • Uptime 99.9%.
  • Час відгуку API < 200 мс для 95% запитів.
  • Відповідність PCI DSS для платежів.
  • Відповідність GDPR для персональних даних.

e-commerce: SDD — архітектурні рішення

Описує, як вимоги реалізовано:

  • API Gateway (Kong) — маршрутизація запитів до мікросервісів, rate limiting.
  • User Service — реєстрація, автентифікація (JWT), управління профілями; PostgreSQL.
  • Product Catalog — MongoDB: гнучка схема для різних категорій товарів.
  • Orders Service — обробка замовлень через saga pattern з координацією через Kafka events.
  • Payment Service — інтеграція зі Stripe API.
  • Notification Service — підписка на Kafka events, відправка email/SNS.
  • Кешування сесій — Redis.

Кожне рішення трасується до вимоги SSD: компонент без вимоги — over-engineering.

e-commerce: ISD — фізична реалізація

Описує середовище виконання архітектури з SDD:

  • Kubernetes-кластер на AWS EKS у двох зонах доступності (eu-central-1a, eu-central-1b).
  • PostgreSQL — кластер primary + 2 read replicas (Patroni); MongoDB — replica set з 3 вузлів; Redis — кластер з 3 нод.
  • Kafka — 3 broker кластер зі schema registry.
  • Моніторинг: Prometheus + Grafana; логи: Loki; трейсинг: Jaeger.
  • CI/CD: GitLab CI з ArgoCD для GitOps-деплою.
  • Бекапи: щогодинні інкрементальні, щоденні повні; retention 30 днів.

Питання 4. Документація та супроводжуваність

Супроводжуваність (Maintainability) — одна з восьми характеристик якості ПЗ за ISO/IEC 25010: здатність до модифікації — виправлення дефектів, адаптація до змін середовища, розширення функціональності.

  • Закони Лемана: програмна система постійно змінюється, і кожна зміна збільшує її складність. Документація — інструмент керування цією складністю: без неї зміни — ризикована операція з непередбачуваними наслідками.
  • Супроводжувана система — чотири пов'язані артефакти: вимоги, код, архітектура, тестові сценарії.
  • Документація — «зв'язуючий шар» між артефактами: забезпечує їхню узгодженість і простежуваність зв'язків.

Модель «четверного зв'язку» (Quadruple Linkage)

Кожен артефакт має двосторонній зв'язок з кожним іншим:

Зв'язокСутьІнструменти документування
Вимоги ↔ КодВимога реалізована в модулі; модуль має прив'язку до вимогиTraceability Matrix; Git refs REQ-001
Вимоги ↔ ТестиВимога покрита тестом; тест валідує вимогуTest Coverage Matrix; теги it('REQ-001')
Архітектура ↔ КодКомпонент має реалізацію; структура коду відображає архмодельSDD + module map; dependency graphs
Архітектура ↔ Тести(unit/integration/e2e) відображає шари та сервісиTest Pyramid; contract tests (Pact)

Розриви зв'язків: Код↔Вимоги → «зайвий код»; Тести↔Вимоги → «сліпі тести»; Архітектура↔Код → «shadow architecture».

Простежуваність (Traceability)

Здатність відстежити ланцюг артефактів від вимоги через архітектуру та код до тестового сценарію:

Пряма (forward):

вимога → код → тест

  • «чи реалізовано всі вимоги?»

Зворотна (backward):

тест → код → вимога

  • «чи кожен тест перевіряє реальну вимогу?»

Матриця простежуваності (RTM)

Requirements Traceability Matrix — таблиця, що зв'язує ідентифікатори вимог з компонентами, модулями коду та тестами.

  • Коли всі чотири зв'язки налаштовані — система «простежувана» (traceable).
  • Зміна вимоги → точково визначаємо, які модулі та тести модифікувати.

Практичні задачі RTM та автоматизація

RTM дозволяє вирішити три задачі:

  1. Покриття вимог (Requirements Coverage): вимога без тесту — не покрита.
  2. Оцінка впливу зміни (Impact Analysis): зміна REQ-003 → одразу видно: Orders Service, orders/create.ts, cart/checkout.ts, тести TC-005/TC-006 — точково, а не повний перегляд системи.
  3. Виявлення «осиротілих» артефактів: тест без вимоги, код без вимоги, вимога без коду.

Сучасна практика: RTM рідко існує як окремий документ — вона інтегрована в інструменти:

  • Jira-тікети: поля «Epic» (вимога) та «Linked PR» (код); тести в Zephyr/TestRail прив'язані до тікетів.
  • Git commits посилаються на номер тікету: refs REQ-001.
  • Це автоматична трасовість, що не потребує ручного підтримання матриці.

Актуальність документації: метрики

Застаріла документація (stale) небезпечніша за відсутню: вона вводить в оману; відсутність принаймні сигналізує про пробіл.

Три метрики актуальності (freshness metrics):

  • Вік останнього оновлення (Last Updated Age): без оновлень > 6 місяців — підозрілий; > 12 — ймовірно застарілий.
  • Частота звернень (Access Frequency): документ, до якого не звертаються місяцами, — можливо, не потрібен.
  • Code-Doc Change Ratio: код змінювався 50 разів за квартал, а документ — жодного → сигнал.

Автоматизація у DaC: співвідношення комітів код/документація; наявність описаних модулів у файловій системі; відповідність OpenAPI-ендпоінтів маршрутам — перевірки в CI/CD.

Стратегії реакції на застарілу документацію

Три правильні стратегії:

  1. Оновити — якщо документ потрібний і просто відстав від коду.
  2. Видалити — якщо не використовується і не має споживача.
  3. Позначити deprecated — якщо історично цінний, але не відображає поточний стан.

❌ Найгірша (четверта) стратегія — «залишити як є»:

  • Лише поглиблює проблему: документ продовжує вводити в оману.
  • Розрив між документацією та системою зростає з кожним релізом.
  • Довіра до документації руйнується остаточно.

Застаріла документація небезпечніша за відсутність — реакція на застарівання має бути обов'язковою і невідкладною.

Передача системи (Handover)

Handover — критична точка життєвого циклу: знання про систему переходять від однієї групи людей до іншої. Без документації передача перетворюється на «передачу знань через усні розмови» — з неминучою втратою і спотворенням інформації, появою «знань, яких уже ніхто не має».

Сценарії передачі:

  • від команди розроблення до операційної (Dev → Ops);
  • від in-house команди до outsourced команди підтримки;
  • при реорганізації компанії;
  • при selling / handover продукту іншій організації.

У всіх випадках документація — універсальний механізм передачі, що не залежить від конкретних людей.

Процес передачі знань (Knowledge Transfer Process)

  1. Аудит документації — перевірка наявності та актуальності всіх документів handover-пакету.
  2. Shadowing — команда супроводу працює поруч із розробниками, вивчаючи систему на практиці.
  3. Reverse shadowing — команда супроводу бере відповідальність; розробники спостерігають і консультують.
  4. Повна передача — розробники виходять із процесу; документація стає єдиним джерелом знань.

Критичний фактор: якість документації протягом усієї розробки, а не лише в момент handover. Принцип Always Ready to Handover: система завжди готова до передачі без втрати знань → DaC.

Підсумки

  • Документація — не додатковий артефакт, а інженерний інструмент: збереження знань, простежуваність рішень, комплаєнс стандартам, здатність системи до еволюції.
  • Різні аудиторії — різні рівні абстракції; головні антипатерни — Documentation Decay та Dead Documentation.
  • Продукт vs процес; технічна / архітектурна / експлуатаційна документація; ЄСПД — каркас мислення, міжнародні наступники — ISO/IEC/IEEE 15289, 26515, 12207.
  • SSD → SDD → ISD — ієрархія трьох рівнів проєктування; ADR зберігає раціональну основу архітектурних рішень.
  • RTM зв'язує вимоги, код і тести в єдину систему знань; регулярний аудит актуальності та Documentation as Code забезпечують довгострокову цінність документації.
