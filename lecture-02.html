Лекція 2. Сучасні підходи, інструменти та автоматизація документування ПЗ.

Назад до змісту лекцій

Лекція 2. Сучасні підходи, інструменти та автоматизація документування ПЗ

План лекції:

  1. Чому класична документація перестала працювати: Word, PDF, Wiki, ритм Agile, ризики відокремлення від репозиторію.
  2. Філософія Documentation as Code: колокація з кодом, Markdown/YAML, контроль версій Git, збірка як артефакт.
  3. Архітектура документації: піраміда рівнів, Single Source of Truth, Git-flow, база знань, ADR, управління актуальністю.
  4. Статичні генератори документації: Docusaurus, MkDocs, Wiki-рішення та критерії вибору.
  5. Документування API та UI: API-first, OpenAPI і Swagger, генерація з коду, Storybook, автоматична публікація, версіонування, Definition of Done.

Питання 1. Чому класична документація перестала працювати

У Лекції 1 розглянуто два фундаментальні антипатерни — Documentation Decay (документація застаріває) та Dead Documentation (існує, але не використовується). Це питання — про їхні кореневі причини.

Теза: класичні формати й процеси документування — текстові процесори, PDF та корпоративні Wiki — архітектурно не відповідають темпу та структурі сучасної інженерії ПЗ.

  • Розрив між документом і системою виникає не тому, що люди «ліниві» або «не цінують документацію», а тому, що інфраструктура документування не має механізмів синхронізації з кодом.
  • Три аспекти тези: властивості класичних форматів; конфлікт із ритмом Agile-розробки; ризики територіального відокремлення документації від репозиторію.

Питання 1.1. Word, PDF та Wiki як «мертві артефакти»

  • Word — бінарний файл: без текстового diff, автоматичний merge неможливий, «історія» — копії виду «ТЗ_финал_v3_остання_правки.docx»; жоден механізм не гарантує, що всі працюють з однією версією.
  • PDF — формат фіксації для друку та остаточної публікації: не передбачає редагування, коментування в рев'ю чи зворотного зв'язку; оновлення — лише повне повторне розміщення файлу.
  • Wiki (Confluence, Notion) частково усуває проблеми: веб-редагування, історія сторінок. Але історія сторінок не інтегрована з історією комітів; зв'язок «зміна поведінки → зміна сторінки» — лише дисципліна авторів; плюс vendor lock-in.
  • «Мертвий артефакт» — документ, зафіксований у момент часу T і не пов'язаний механічним зв'язком із системою, що еволюціонує. Він може бути бездоганним, але його актуальність — випадкова величина.

Питання 1.2. Agile, часті релізи та проблема актуальності

  • Каскадна епоха: реліз раз на 6–18 місяців; точка синхронізації — завершення етапу; документ «заморожувався» перед випуском. Класична ЄСПД описувала саме такий ритм.
  • Continuous Delivery знищив точку синхронізації: production змінюється щодня або щотижня; великі платформи випускають десятки релізів на добу.
  • Арифметика розриву: 30–50 затверджених змін коду на місяць при документації «як з'явиться час» → за квартал документ описує неіснуючу систему: видалені ендпоінти, перейменовані модулі, змінені ліміти.
  • Швидкість дрейфу документації пропорційна частоті релізів; компенсувати її можуть лише процеси з тією самою частотою синхронізації.

Agile і документація: маніфест та ISO 26515

  • «Agile не вимагає документації» — хибне трактування маніфесту. «Working software over comprehensive documentation» — пріоритезація цінностей, а не скасування документації.
  • Різниця між «вичерпною» (comprehensive) та «корисною» (valuable) — принципова. Agile вимагає документувати те, що має споживача тут і зараз: критерії приймання, контракти API, Definition of Done.
  • ISO/IEC/IEEE 26515 («Developing information for users in agile development») прямо узаконює зв'язок: інформація для користувачів розробляється ітеративно й інкрементально — в тому самому ритмі, що й функціональність.
  • Висновок: проблема не в Agile як такому; проблема в процесах документування, спроєктованих для каскадної епохи й не перебудованих під новий ритм.

Питання 1.3. Документація поза репозиторієм = ризик

Git-репозиторій — єдине місце «правди» про систему: код, тести, конфігурації, CI-конвеєри. Документація поза цим контуром створює друге «джерело істини», а двох джерел істини не існує.

  • Розрив зв'язку зміни: автор коду не бачить документацію поруч і не оновлює її «за замовчуванням».
  • Розрив рев'ю: рев'юер, що затверджує зміну поведінки, не бачить документацію і не відповідає за неї.
  • Розрив пошуку: знайти відповідь у коді простіше, ніж сторінку в Wiki → «племінні знання» витісняють документацію.
  • Комплаєнс-ризик: аудитор ISO/IEC 27001 / CMMI отримує документ, що не відповідає реалізації → non-conformity → коригувальні дії (CAPA).

Висновок питання 1: проблема — архітектура процесу

  • Проблема не в людях і не в ставленні до документації: класична інфраструктура не має механізмів синхронізації з кодом, і жодна особиста дисципліна не компенсує цей структурний дефект системно.
  • Bus Factor (Лекція 1): коли знання живуть у головах і в Wiki, куди ніхто не заглядає, кадрова втрата подвійна — система втрачає і людину, і адекватний опис.
  • З документацією, що «живе» в колективній пам'яті, не працює жоден механізм масштабування: пам'ять команди з 5 інженерів не масштабується на 50.

Рішення: перенести документацію туди, де живе зміна системи — у репозиторій, під контроль версій, рев'ю та конвеєр CI/CD. Це Documentation as Code (питання 2).

Питання 2. Філософія Documentation as Code (DaC)

Documentation as Code (DaC) — підхід, за якого документація трактується як повноправний інженерний артефакт: зберігається в текстових форматах у тому самому репозиторії, що й код; контролюється системою контролю версій; проходить рев'ю; збирається та публікується автоматичним конвеєром.

  • Формула: до документації застосовуються ті самі інженерні практики, що й до програмного коду.
  • Ідея оформилася на початку 2010-х у спільноті Write the Docs; сьогодні DaC — індустріальний стандарт.
  • Документація React, Kubernetes, Python та більшості великих платформ — це Markdown-репозиторії зі збіркою через статичні генератори.

Чотири складові філософії DaC: документація як частина коду; текстові формати розмітки; контроль версій; документація як build-артефакт.

Питання 2.1. Документація як частина коду

  • Колокація: документація живе в тому самому репозиторії й має той самий життєвий цикл, що й код: народжується в гілці, проходить рев'ю, зливається, версіонується, супроводжується разом із функціональністю.
  • Механічний зв'язок: зміна поведінки системи — один Pull Request з кодом і документацією разом; рев'юер бачить їх поруч. Незгода з документацією блокує злиття так само, як незгода з кодом.
  • Охоплення: README, SSD, SDD, ADR, OpenAPI, діаграми як код (Mermaid, PlantUML), changelog, runbooks. Критерій: якщо артефакт описує систему і має споживача — йому місце в репозиторії.
  • Культурний зсув: автор зміни відповідає за її опис, техрайтер — за структуру і навігацію, архітектор — за рішення. Technical writer еволюціонує від «письменника» до інженера інформаційної архітектури.

Питання 2.2. Markdown, YAML

Markdown — розмітка де-факто DaC (стандарти CommonMark та GFM). Ключова властивість — plaintext-читабельність: файл читається без жодного інструменту, diff — звичайний текстовий diff.

# Послуга Payment Service
Модуль обробки платежів через зовнішні шлюзи.
## Ендпоінти
- `POST /api/v1/payments` — створити платіж
- `GET /api/v1/payments/{id}` — отримати статус
## Обмеження
| Параметр       | Межа        |
|----------------|-------------|
| Rate limit     | 100 req/хв |
| Таймаут шлюзу  | 30 с        |
> Примітка: retry лише для ідемпотентних операцій (ADR-0004)

Розширення: MDX (Markdown + React-компоненти, основа Docusaurus), AsciiDoc, reStructuredText (Python, Sphinx). Вибір формату — архітектурне рішення: він визначає інструменти збірки та портативність.

YAML: метадані документів

YAML — структурована конфігурація, читабельна людині і машині. У документації — дві функції:

  • Front matter: YAML-блок на початку кожного Markdown-файла — назва, власник, статус, дата перегляду; основа автоматизованого аудиту актуальності (Лекція 1).
  • Специфікації: OpenAPI-контракти, конфігурація CI та генераторів документації пишуться на YAML.
---
title: Payment Service — керівництво
owner: payments-team@
status: published
  # draft | in-review | published
  # | deprecated
review_date: 2026-03-15
tags: [payments, api, v2]
---

Діаграми як код (Diagrams as Code)

  • Замість «мертвих» PNG-знімків із Visio архітектурні діаграми зберігаються як текст: Mermaid (flowchart, sequence, C4), PlantUML, Structurizr DSL.
  • Діаграма має історію змін, проходить рев'ю як текст і регенерується при збірці документації.
  • Для Enterprise-масштабу це критично: діаграма, яку не можна відредагувати як текст, неминуче відстає від архітектури, яку зображує.
  • Типове зберігання в DaC-репозиторії: docs/architecture/diagrams/*.mmd поруч із SDD і ADR.

Питання 2.3. Version control через Git

  • Інструментарій Git: git log — еволюція; git blame — хто і навіщо змінив твердження; гілки — чернетки; теги — стан релізу (docs-v2.3.0).
  • CODEOWNERS призначає обов'язкових рев'юерів для шляхів документації — «власник документа» з Лекції 1 інженерними засобами.
  • Археологія рішень: чому документація стверджує X — відповідь у коміті з посиланням на ADR/тікет.
  • Чесність: Git не вирішує актуальність автоматично; без процесних правил DaC вироджується в «ще одне Wiki» — застарілий Markdown бреше так само.
# .github/CODEOWNERS — обов'язкові рев'юери документації
/docs/                     @tech-writers @lead-dev
/docs/architecture/adr/    @architects
/docs/api/                 @backend-leads
*.md                       @tech-writers

Питання 2.4. Документація як build-артефакт

Документація збирається конвеєром, як бінарник з вихідного коду: lint → build → test → deploy.

«Документація, що не збирається, не їде»: зламана розмітка ламає build, як зламаний тест — CI. Відтворюваність: вимоги Configuration Management (ISO 9001, CMMI) DaC дає «безкоштовно».

Питання 3. Архітектура документації в проєкті

Як і програмна система, документація потребує архітектури — свідомо спроєктованої структури, що відповідає аудиторіям (Лекція 1), життєвому циклу системи та процесам команди.

  • Хаотична «папка з файлами» породжує ті самі проблеми, що й неструктурований код: неможливість знайти потрібне, дублювання, деградацію.
  • Розглянемо: структуру документації за рівнями; принцип єдиного джерела істини; інтеграцію з Git-процесом; організацію корпоративної бази знань; практику ADR; управління актуальністю під час розвитку системи.

Питання 3.1. Піраміда документації: README → Architecture Docs

РівеньЗмістАудиторіяПитання

Питання 3.2. Single Source of Truth

SSOT: кожен факт існує рівно в одному місці; решта згадок посилається на нього або генерується з нього. Дублювання гарантує розсинхронізацію: SLA «99,9%» у презентації і «99,5%» в угоді — юридичний конфлікт.

Механізми DaC, недоступні в Word-епосі:

  • Вбудовування (transclusion): сніпети MkDocs / Docusaurus включають один фрагмент у кілька сторінок — правка джерела оновлює всі.
  • Генерація замість копіювання: версія API в README генерується з OpenAPI при збірці.
  • Параметризація: спільні величини (адреси, ліміти, назви) — в один файл даних.

SSOT: антипатерни та DaC-рішення

SSOT масштабується на організацію: платформена документація — єдине джерело, командні — лише посилаються. Компроміс: джерела істини мають найсуворіший режим підтримання — обов'язкове рев'ю, призначений власник, автоматичні перевірки.

Питання 3.3. Документація і Git-flow

Модель робочого процесу коду (Trunk-Based Development, GitHub Flow, Git-flow) визначає й модель документації: вони мають бути ізоморфними. Розгалуження процесів («код у гілках, документи на Wiki») — попередження про майбутній дрейф.

Подія процесуДія документації

«Docs-or-don't-merge» та великі перепрацювання

  • «Документуй — або не зливаємо»: PR, що змінює публічну поведінку — новий ендпоінт, інша конфігурація, інший формат відповіді, — не зливається без оновлення документації.
  • Правило закріплюється шаблоном PR: чек-лист містить пункт «Документацію оновлено (docs/, OpenAPI, CHANGELOG)»; рев'юер має право відхилити PR за його відсутністю.
  • Великі перепрацювання (новий розділ, міграція бази знань) — та сама механіка, що рефакторинг коду: довгоживуча гілка, поетапні PR, рев'ю з власником.
  • Документація ніколи не «переписується з нуля за вихідні» — так само, як код не переписують за одну ніч без рев'ю.

Питання 3.4. Організація корпоративної бази знань

Корпоративна база знань — не «сума всіх README», а система зі структурою, регламентом і власниками з керованим життєвим циклом документів: Draft → In Review → Published → Deprecated → Archived. Wiki «для всього» без правил за рік стає некерованим звалищем сторінок.

  • Структура віддзеркалює знання організації: розділи продуктів, платформені (спільна інфраструктура), процесні (регламенти), онбординг-кущ.
  • Developer portal за зразком Backstage (продукт Spotify): каталог сервісів з документацією, власниками та статусами — «інвентар Enterprise».
  • Obsidian (інструмент курсу): Markdown-граф знань (wikilinks, теги, backlinks); кущі ADR/RFC — ланцюг рішень; індекси за front matter. Основа — файли в Git: усі переваги DaC.

Регламент — міні-стандарт у дусі ISO 9001: база знань — керований об'єкт з ідентифікацією, власником, контролем змін і записом статусу. Організації, що проходять оцінювання за CMMI, демонструють такі регламенти як доказ рівня 3 (Defined process).

Питання 3.5. Документування архітектурних рішень (ADR)

Архітектурне рішення — вибір із довгостроковими наслідками, який дорого переглядати. ADR — короткий (1–2 сторінки) незмінюваний документ: одне рішення з контекстом, альтернативами і наслідками. Набір ADR — «хроніка архітектури»: ланцюг рішень, а не «так історично склалося».

  • Незмінюваність: прийнятий ADR не редагується — нове рішення створює новий запис; попередній отримує статус Superseded.
  • Нумерація і каталог: ADR-0001, ADR-0002, … у docs/architecture/adr/ — кожен знайдено за номером.
  • Статуси життєвого циклу: Proposed → Accepted → Deprecated / Superseded; ланцюг «superseded by ADR-N» веде від старого рішення до актуального.

ADR: критерій доцільності та інструменти

  • Критерій — «двері без повернення» (one-way door): запису потребує рішення, яке дорого переглядати; дрібні вибори (назва змінної, колір банера) ADR не потребують.
  • ADR застосовні до будь-яких значущих інженерних виборів, не лише до вибору бази даних: наступний приклад документує вибір інструмента документації команди.
  • Інструменти практики: adr-tools (CLI для створення нумерованих записів), формат MADR (Markdown Annotated ADR), кущі ADR в Obsidian з автопосиланнями між записами.

ADR: шаблон та приклад реального запису

# ADR-NNNN: <Назва рішення>
- Статус: Proposed | Accepted |
  Deprecated | Superseded by
  ADR-MMMM
- Дата: 2026-10-22
- Автор: <ім'я, роль>
## Контекст
Яка сила тисне на рішення:
вимоги, обмеження, ризики.
## Розглянуті альтернативи
1. <Альтернатива A> — плюси, мінуси
2. <Альтернатива B> — плюси, мінуси

Обрано <X>, тому що
<зважування аргументів>.

нові ризики; чи є це «дверима

Питання 3.6. Три типи дрейфу документації

Актуальність — не стан, а безперервний процес. Контур DaC повторює контур якості коду: зміна системи → автоматична перевірка → сигнал про розрив → виправлення → публікація.

Тип дрейфуСутьМеханізм контролю в DaC
Змістовий (content drift)Твердження не відповідають поведінці: метод описаний, а вже видалений; ліміти не тіПроцесний: оновлення в тому самому PR, рев'ю, щоквартальний аудит за review_date
Структурний (structure drift)Описана структура не відповідає реальній: сервіс розколовся на два, а в SDD він одинДіаграмний: діаграми як код регенеруються з тієї самої гілки; рефакторинг змушує оновити текст
Контрактний (API drift)Документація API і реалізація розходяться — найнебезпечніший: вдаряє по зовнішніх клієнтахАвтоматичний: контрактне тестування порівнює OpenAPI з реальними маршрутами; розрив ламає CI

Застаріла документація — технічний борг

  • Застаріла документація — категорія технічного боргу: як і борг коду, вона має «проценти» — щодня невідповідності накопичуються і роблять кожну подальшу зміну дорожчою.
  • Організації, що монетизують технічний борг (перерахунок вартості усунення в людино-години), враховують і борг документації: витрати на повторні пояснення, помилкові інтеграції, повільний онбординг.
  • Стратегія та сама, що для коду: безперервне виправлення дрібними кроками в кожному спринті, а не «генеральне переписування раз на рік».

Питання 4. Статичні генератори документації

Практичний інструмент збірки DaC — статичні генератори сайтів (Static Site Generators, SSG): перетворюють каталог Markdown-файлів на готовий вебсайт з навігацією, пошуком і версійністю — без баз даних і серверного коду, тобто «статично».

  • Два індустріальні стандарти: Docusaurus та MkDocs.
  • Клас Wiki-рішень (Confluence, Notion), що досі поширені в корпоративному світі.
  • Сформулюємо критерії вибору генератора для конкретного проєкту.

Питання 4.1. Docusaurus: масштабованість, версійність, локалізація

Docusaurus — продукт Meta з React-екосистеми (документація React та багатьох платформ). Архітектура — MDX + плагіни: живі приклади коду, таблиці API, банери.

  • Версійність: кожен реліз документації «снімкується» (docusaurus docs:version): незалежні гілки /docs/2.x і /docs/3.x.
  • Локалізація (i18n): десятки мов; один сайт з перемикачем мови. Плагіни: блог, сторінки, пошук (Algolia).
  • Слабкі сторони: Node.js-навички, складніша конфігурація, повільніша збірка.

Коли обирати: документація — це продукт — публічні платформи, багатомовність, брендинг, кастомні компоненти.

Docusaurus: фрагмент конфігурації

// docusaurus.config.js — фрагмент конфігурації
const config = {
  url: 'https://docs.example.com',
  baseUrl: '/',
  i18n: {
    defaultLocale: 'uk',
    locales: ['uk', 'en', 'de'],
  },
  presets: [
    [
      '@docusaurus/preset-classic',
      {
        docs: {
          routeBasePath: 'docs',
          // версійні знімки документації релізів
          versions: {
            current: { label: 'v3 (dev)' },
          },
        },
        blog: false,
      },
    ],
  ],
};

Питання 4.2. MkDocs: простота і швидкий старт

MkDocs — генератор з Python-екосистеми: каталог Markdown-файлів і один mkdocs.yml; крива входу — хвилини, ідеально для початку DaC.

  • mkdocs new — каркас; mkdocs serve — живий прев'ю; mkdocs gh-deploy — GitHub Pages.
  • Стандарт — Material for MkDocs: адаптивний дизайн, пошук, Mermaid, git-revision-date (правки з Git — метрика актуальності), mike, сніпети (SSOT).
  • Обмеження: тема, а не фреймворк — складнощі з кастомізуванням; версійність лише через mike; без MDX.
  • Культурне порівняння: Docusaurus — «фреймворк документації» для платформних команд; MkDocs — «інструмент інженера» для баз знань; обидва — DaC-сумісні.

MkDocs: конфігурація бази знань команди

Питання 4.3. Wiki-рішення: ніша та «вузьке місце»

Сильні сторони Wiki (Confluence, Notion):

  • нульовий поріг: редагування в браузері, без Git-навичок;
  • нетехнічні автори (менеджери, аналітики) пишуть вільно;
  • неформальна співпраця: нотатки, брейншторм, чернетки;
  • вбудовані таблиці та макроси; корпоративний пошук і SSO.

Wiki — «вузьке місце», якщо заміщує документацію продукту:

  • немає зв'язку з репозиторієм — ризики питання 1.3;
  • редагування без рев'ю неприйнятне для комплаєнсу;
  • тисячі сторінок без власників — «цивинтар документів»;
  • контент у пропрієтарній базі, міграція — місяці.

Гібридна архітектура корпоративної документації

Практичний висновок — гібрид із чітким розмежуванням:

  • документація продукту, архітектури та експлуатації (усе, що має версії, рев'ю і зв'язок з кодом) — DaC у репозиторії;
  • процесна і комунікаційна документація (наради, регламенти для нетехнічних ролей) — Wiki.

Межа проста: документ описує систему і розвивається разом із нею — йому місце в Git; описує хід роботи людей і має коротке життя — Wiki достатньо.

Критерії вибору інструменту для кожного класу задач — на наступному слайді.

Питання 5. Документування API та UI: автоматизація

Завершальне питання — автоматизація документування там, де воно можливе найповніше: у контрактах API та інтерфейсах користувача.

Ключова теза: документація API та UI-компонентів має не писатися, а генеруватися з єдиного джерела — специфікації або коду — і публікуватися автоматично в контурі CI/CD.

  • Підхід API-first та специфікація OpenAPI; екосистема Swagger.
  • Генерація документації безпосередньо з коду; Storybook для UI.
  • Автоматична публікація при злитті; версіонування документації.
  • Інтеграція документації в Definition of Done та перевірки CI/CD.

Питання 5.1. Документація API — не опція. Підхід API-first

API — публічний контракт: якщо система надає сервіси іншим системам, документація API — частина продукту. Розробник-інтегратор не читає ваш код: його єдине вікно в систему — специфікація. Погано документований API — звернення в підтримку, невірні інтеграції, інциденти, втрата клієнтів — прямі втрачені доходи платформи.

  • API-first: контракт (OpenAPI) створюється до реалізації і є першим артефактом функціональності: «узгодили контракт → згенерували стаби і моки → реалізували».
  • Наслідки: фронтенд, бекенд, QA і клієнти працюють паралельно з однієї специфікації; мок-сервер (Prism, WireMock) дає інтеграцію до готовності бекенду; тести валідують відповіді до написання UI.

API-first vs Code-first: напрям SSOT контракту

  • Code-first (специфікація генерується з анотацій коду) vs API-first (специфікація є джерелом) — вибір напряму SSOT для контракту.
  • API-first виграє в керованості: контракт проходить рев'ю до того, як у коді з'явилися наслідки; breaking changes видно на етапі diff'у специфікації, а не в інцидентах клієнтів.
  • Code-first виграє в швидкості старту і годиться для внутрішніх сервісів.
  • Для систем із зовнішніми споживачами індустрія сходиться на API-first з обов'язковим лінтингом контрактів.

Питання 5.2. OpenAPI — мова комунікації між командами

OpenAPI Specification (OAS) — машинно-читний стандарт опису REST API (спадкоємець Swagger, гілка 3.x): операції (paths), параметри, схеми даних, коди відповідей, автентифікація (OAuth2, API key). Один файл — одночасно контракт, документація, основа SDK і тестів.

  • Специфікацію читають усі ролі: бекенд (реалізує), фронтенд (генерує клієнт), QA (генерує тести), техрайтер (публікує довідку), DevOps (gateway), зовнішні партнери.
  • Формат знімає двозначності: не «приблизно id», а схема Order з полями, типами, прикладами.
  • У DaC специфікація живе в docs/api/, проходить рев'ю і лінтиться (Spectral): описи, приклади, узгоджені коди помилок.

OpenAPI: фрагмент специфікації сервісу платежів

openapi: 3.1.0
info:
  title: Payment Service API
  version: 2.4.0

  /payments/{id}:

      summary: Отримати статус платежу
      parameters:
        - { name: id, in: path, required: true,
            schema: { type: string, format: uuid } }
      responses:
        '200':
          description: Поточний статус платежу
          content:
            application/json:
              schema: { $ref: '#/components/schemas/Order' }
        '404':
          description: Платіж не знайдено
components:
  schemas:
    Order:
      type: object
      required: [id, status, amount]
      properties:
        id:      { type: string, format: uuid }
        status:  { type: string, enum: [new, pending, paid, failed] }
        amount:  { type: number, example: 199.99 }

Екосистема Swagger

  • Swagger UI — інтерактивна документація: кнопка «Try it out» викликає API з браузера — документація стає пісочницею, поріг інтеграції падає.
  • Swagger Editor — редактор YAML із живим попереднім переглядом і валідацією: помилки схеми підкреслюються одразу, а не при збірці.
  • Swagger Codegen / OpenAPI Generator — з одного контракту генерують SDK для десятків мов (TypeScript, Python, Java, Go), серверні стаби і довідку — SSOT у дії: контракт один, артефактів багато.

Повний цикл: Editor — автор, UI — споживач, Codegen — автоматизація. Межа: OpenAPI документує «що викликається», але не замінює наративні гайди «чому і як правильно» — вони лишаються в Markdown.

Питання 5.3. Генерація документації безпосередньо з коду

Docstring-генератори збирають довідник API з анотацій у коді: опис живе над функцією, рев'юер бачить їх разом. Збірка — в CI тим самим конвеєром, що й сайт документації.

ЕкосистемаІнструментиОсобливості
JavaJavadocСтандарт @-анотацій; HTML-вихід
PythonSphinx + autodoc; mkdocstringsdocstring → сайт (поєднання з MkDocs)
JavaScript / TypeScriptJSDoc, TypeDocТипи TypeScript — джерело схем
.NET (C#)DocFXXML-коментарі → повний сайт довідки
C / C++DoxygenДовідка і діаграми залежностей із коду
GogodocКонвенція «коментар = документація»

Генерація з типів і схем

  • Окремий підвид — генерація з типів і схем: TypeScript-типи → JSON Schema → документація; Protocol Buffers / gRPC → довідник сервісів; SQL-схеми з коментарями таблиць → ER-діаграми.
  • Принцип той самий: чим ближче джерело документації до єдиного «файлу правди» (типу, схеми, контракту), тим менше точок розсинхронізації.
  • Чесне обмеження генерації з коду: згенерована документація описує «як викликається» (сигнатури, параметри, типи), але погано — «чому» і «як правильно» (сценарії, компроміси, обмеження).

Тришарова модель документації API

Індустріальна практика — три шари, що не дублюють, а посилаються один на одного:

ШарФорматВідповідає на питання
1. Наративні гайдиMarkdown«Чому і як правильно» — сценарії, компроміси
2. КонтрактиOpenAPI«Що викликається» — операції, схеми, помилки
3. Згенерований довідникJavadoc, TypeDoc, Doxygen…«Сигнатури і деталі»

DaC-практика: метрика «покриття документації» (частка публічних API з описами) автоматично перевіряється в CI — лінтер TypeScript на doc-коментарі, прапорець генерації .NET, правила Spectral для OpenAPI. Задокументований публічний API — критерій Definition of Done.

Питання 5.4. Storybook: жива документація UI

UI — друга область відставання документації: скріншоти старіють, стани компонентів недокументовані, Figma-макет ≠ реальний компонент. Storybook — індустріальний стандарт: ізольоване середовище розробки UI-компонентів, де компонент відображається поза застосунком, у «пісочниці», у вигляді stories — варіантів стану: звичайний, hover, disabled, loading, error, порожні дані, переповнення.

  • «Жива документація»: сторінки Storybook — не знімки; вони рендеряться з реального коду компонента при кожному відкритті. Змінився компонент — змінилася і сторінка: така документація не може застаріти.
  • Docs-сторінки (MDX) поєднують текст, таблиці пропсів (генеровані з типів) і живі stories — єдиний довідник компонента.

Storybook у контурі Design System

Для організацій з Design System (єдина бібліотека компонентів) Storybook виконує роль каталогу системи:

  • Дизайнери описують варіанти компонентів → розробники реалізують компонент і stories → QA додає interaction-тести прямо в stories → Chromatic (візуальні регресійні тести) фіксує зміни вигляду.
  • Дизайн-рев'ю переноситься в живе середовище: дизайнер бачить не картинку, а реальний компонент з реальними даними; зникає ланцюжок «Figma → верстка → розсинхронізація».
  • У DaC-контурі stories живуть у репозиторії поруч із компонентами, проходять PR-рев'ю разом з ними і публікуються автоматично при злитті — Storybook Docs — той самий статичний build-артефакт, що й сайт документації.

Storybook: stories для кнопки Design System (CSF)

// src/components/Button/Button.stories.tsx
import type { Meta, StoryObj } from '@storybook/react';
import { Button } from './Button';

const meta: Meta<typeof Button> = {
  title: 'Design System/Button',
  component: Button,
  parameters: {
    docs: {
      description: {
        component: 'Основна кнопка Design System: варіанти ' +
                   'кольорів, розмірів та станів. ' +
                   'Див. ADR-0012 (токени темізації).',
      },
    },
  },
};
export default meta;
export const Primary: StoryObj<typeof Button> = {
  args: { variant: 'primary', label: 'Оплатити' },
};
export const Disabled: StoryObj<typeof Button> = {
  args: { variant: 'primary', label: 'Оплатити', disabled: true },
};
export const ErrorState: StoryObj<typeof Button> = {
  args: { variant: 'primary', label: 'Помилка шлюзу', state: 'error' },
};

Питання 5.5. Публікація при merge. GitHub/GitLab Pages

«Опублікувати документацію» в DaC — стадія конвеєра: злиття в main запускає збірку і деплой. Не можна «забути опублікувати» чи опублікувати зламане.

  • GitHub / GitLab Pages — безкоштовні статичні хостинги: домени, HTTPS, розгортання з гілок (GitHub Actions або job pages → public/); Netlify / Vercel — preview-деплої на кожен PR.
  • Режим strict: попередження MkDocs — мертве посилання, сторінка поза навігацією — ламає конвеєр: «документація, що не збирається, не їде».
  • Preview-деплой на кожен PR: тимчасова адреса зі документацією зміни — рев'ю стає візуальним, а не «уявним за diff-ом».

CI: публікація документації (GitHub Actions)

# .github/workflows/docs.yml — публікація документації
name: Docs Deploy
on:
  push:
    branches: [main]          # публікація при merge в main

permissions:
  contents: read
  pages: write
  id-token: write

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with: { python-version: '3.12' }
      - run: pip install mkdocs-material
      - run: mkdocs build --strict    # strict: зламана розмітка = fail
      - uses: actions/upload-pages-artifact@v3
        with: { path: 'site' }

  deploy:
    needs: build
    runs-on: ubuntu-latest
    environment: { name: 'github-pages' }
    steps:
      - uses: actions/deploy-pages@v4

Питання 5.6. Versioning документації

Проблема: клієнт на v1.9, що читає документацію v2.4, отримає інструкції, які не працюють. Стратегії: версійність гілками (документація версії = гілка v1.x; виправлення — backport-ом); каталогами (Docusaurus: docs/ + versioned_docs/version-2.4/); знімки релізів (tag → архів документації релізу).

Подія релізуДія документації
Мінорний реліз (2.4)Допис нових розділів у поточну версію; запис у changelog
Мажорний реліз (3.0)Новий знімок документації v3.0; міграційний гайд 2.x → 3.0; попередження на v2.x
Виведення функції з експлуатаціїDeprecation-нотатки в changelog, документації і відповідях API (заголовки Sunset)
Підтримка старої гілки (2.x)Бекпорти виправлень документації разом із кодом

Політика версіонування документації

  • Документація найновішої стабільної версії — за замовчуванням; на сторінках старих версій — попередження («ви читаєте v2.3 — актуальна v3.0»).
  • Кожен мажорний реліз створює нову версію документації та міграційний гайд (upgrade guide): breaking changes документуються до релізу, в тому самому PR.
  • Deprecation-нотатки розходяться трьома каналами: changelog, документація і — для API — відповіді сервера (заголовки Sunset), щоб про виведення з експлуатації дізналася й автоматика клієнтів.
  • Версія документації = релізний тег коду: версіонування в DaC — не окремий процес, а частина релізного конвеєра: розрізали release-гілку → створили версію → опублікували — без жодного ручного кроку.

Питання 5.7. Документація як частина Definition of Done

DoD — узгоджений командою перелік критеріїв завершеності. Якщо «документація оновлена» — критерій готовності, а не побажання, актуальність не залежить від доброї волі авторів. Документаційний блок DoD:

Критерій DoDЩо перевіряєтьсяМеханізм контролю
Документація поведінкиОновлено docs/ для змін публічної поведінкиРев'ю PR; CODEOWNERS
Контракт APIopenapi.yaml: описи, приклади, коди помилокSpectral lint у CI
Архітектурні рішенняДля значущих рішень створено ADRРев'ю архітектором
CHANGELOGЗапис за форматом Keep a ChangelogCI-перевірка запису в PR
UI-компонентиStories оновлено для змінених компонентівЗбірка Storybook у CI
МіграціяBreaking changes → міграційний гайдРев'ю + версійність (5.6)

Автоматичні перевірки у CI/CD

Другий важіль — перевірки, що перетворюють відповідність документації реалізації з надії на механіку. Мінімальний індустріальний набір:

  • markdownlint (синтаксис) та Vale (стиль технічного письма: коротко, активним станом, без жаргону).
  • Перевірка посилань (lychee, htmltest) — мертвий лінк ламає збірку.
  • Spectral — лінтинг OpenAPI: наявність описів, прикладів, узгоджених кодів помилок.
  • Docs coverage — частка публічних API і компонентів з описами; freshness — прострочені review_date з front matter.

Контрактний дрейф та QA Governance

Найсильніша перевірка — виявлення контрактного дрейфу (API drift): CI порівнює специфікацію в репозиторії з фактичною поведінкою реалізації. Інструменти: Schemathesis, Dredd (контрактне тестування — генерація запитів зі специфікації та перевірка відповідей) або diff між згенерованою з коду специфікацією і збереженою. Будь-яка розбіжність ламає конвеєр. Ефект: «документація бреше» стає технічно неможливою подією — як зламаний тест.

QA Governance для документації: метрики doc-rot, freshness, coverage на дашбордах (SonarQube, Grafana) поруч із метриками коду; власники і статуси документів; періодичні аудити. Результати аудиту актуальності — частина звіту про технічний борг перед бізнесом.

Підсумки

  • Класичні формати (Word, PDF, Wiki) — «мертві артефакти»; Agile загострив проблему частоти релізів.
  • Формула DaC: Markdown/YAML + Git + рев'ю в Pull Request + автоматична збірка і публікація в CI/CD.
  • Архітектура (піраміда README → … → Architecture Docs, SSOT, ADR, регламент бази знань) — «що і де документувати».
  • Інструменти (MkDocs, Docusaurus, OpenAPI/Swagger, Storybook, Pages) — «чим збирати і публікувати».
  • Процесні важелі (DoD, лінтери, контрактне тестування, перевірки дрейфу) — «як гарантувати відповідність реалізації».

Спільна теза блоку: сучасна документація — інженерна система з життєвим циклом, метриками і конвеєром. Лекція 3 — супровід і експлуатація.
